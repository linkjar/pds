# Upstream 0.5.35 to 0.5.37 against the frozen pin

Research record, 2026-10-10. Companion to [SPEC.md](../SPEC.md) §2, §6 and
§13 and to the patch-stack decision in [plan.md](../plan.md). It records what
upstream released after the pin, classifies each change, examines
[bluesky-social/atproto#5584](https://github.com/bluesky-social/atproto/pull/5584)
for LinkJar's deployment, and gives a recommendation. The pin decision is the
owner's. This note changes no pin.

**Method.** Pull requests, reviews and changelogs read through the GitHub
API. Diffs read in a sparse checkout of `bluesky-social/atproto` at the pin
`7ca16cc6989f8247637615aca17c5abb911b8fb1` and at the three release commits:
0.5.35 `ad725520ff6441902cf448c5c7b8741b5ccf05cf`, 0.5.36
`ee49be8109bc2f91b112fdbc1e46747b05411f7f`, 0.5.37
`a7c8604d876a200a1e4fa4aec83d4189ac4f1c12`. Each "measured" statement was
produced on 2026-10-10 with `git apply` in that checkout. Nothing was built
and no server was run.

**Limit of this note.** No repository with a shared node was built, and the
Reference was not timed on one. The note says which code paths #5584 changes
and who can reach them. It gives no construction and no cost figure.

## 3. #5584 and the import path

**What upstream changed.** Every traversal that can enter more than one
child of an MST node now keeps a set of the node CIDs it has entered and
throws `VisitedCidError` on a repeat: `walk`, `walkFrom`, `paths`,
`allCids`, `walkReachable`, `getUnstoredBlocks`, `carBlockStream` and
`MstWalker`, which drives `mstDiff`. `importRepo` maps the error to 400
`InvalidRequest`, "invalid MST: node referenced more than once: <cid>".
Record value CIDs are not marked, because two records with the same content
share one. Lookups that follow one path are exempt.
Source: commit [`a6561d5`](https://github.com/bluesky-social/atproto/commit/a6561d54227756876a0901e4a87675df17972d32),
six source files in `packages/repo/src` and `importRepo.ts`.

**What that says about the pin.** The changelog states the reason: the
traversals "now throw `VisitedCidError` instead of re-walking shared
subtrees, bounding their cost by the number of unique blocks". At the pin
the same traversals keep no such set. By upstream's description the work of
an import is then not bounded by the number of blocks in the upload. How
far it can exceed the upload was not measured here.

**Which request reaches it.** `com.atproto.repo.importRepo` reads the CAR
into memory and calls `verifyDiff`, which calls `DataDiff.of` and so
`mstDiff` over the uploaded tree. The pull request states that this is the
only API handler that diffs a repository a client supplied. The call runs
inside the actor store transaction of the calling account.
Source: [`importRepo.ts`](https://github.com/bluesky-social/atproto/blob/7ca16cc6989f8247637615aca17c5abb911b8fb1/packages/pds/src/api/com/atproto/repo/importRepo.ts) lines 37 to 63;
[`sync/consumer.ts`](https://github.com/bluesky-social/atproto/blob/7ca16cc6989f8247637615aca17c5abb911b8fb1/packages/repo/src/sync/consumer.ts) lines 56 to 77;
[`mst/diff.ts`](https://github.com/bluesky-social/atproto/blob/7ca16cc6989f8247637615aca17c5abb911b8fb1/packages/repo/src/mst/diff.ts).

**Who may call it.** A session with full access, or an OAuth session whose
permissions include `account:repo?action=manage`. An app password is not
enough. A taken-down account is refused; a deactivated account is not,
because a migrating account imports before it activates. The handler gives
`verifyDiff` neither a DID nor a signing key, at the pin and at 0.5.37, so
the caller does not need the account's signing key to submit a tree.
Source: `importRepo.ts` lines 21 to 27 and 54 to 61; `auth-scope.ts` line 11.

**What bounds the request at the pin.** Imports are on unless
`PDS_ACCEPTING_REPO_IMPORTS` is `false`. The body is capped at
`PDS_MAX_REPO_IMPORT_SIZE`; without it the cap is the blob upload limit,
5 MiB by default. No rate limit is specific to the method: the only limit
that applies is the global one of 3,000 requests per address in five
minutes.
Source: `packages/pds/src/config/config.ts` lines 39 to 41, `index.ts`
lines 159 to 162 and `rate-limits.ts` lines 31 to 45;
`packages/xrpc-server/src/server.ts` line 645, all at the pin.

**Stored trees.** If the pin accepts such an import, the tree is in the
actor database. `sync.getRepo`, which needs no authentication, then streams
it through `carBlockStream`. At 0.5.37 that stream throws for such a
repository; the reviewer of #5584 notes this as a change beyond the one
handler. Whether the pin accepts the import or fails in another way was not
observed.
Source: `repo/src/sync/provider.ts` line 27 and `repo/src/mst/mst.ts` line
727 at the pin; the review comment on #5584 of 2026-10-02.

### 3.1 Exposure of LinkJar's deployment

- **One account is enough.** LinkJar's sign-up runs through OAuth with
  hCaptcha or a provider, and patch 099c keeps `createAccount` open for a
  migration whose service token names the DID being imported
  ([provider-policy.md](../legacy/provider-policy.md), "Legacy signup
  boundary"). Either route gives a session that may call `importRepo`. An
  invitation requirement narrows who can sign up; it does not change what an
  account can do.
- **Imports are on unless the host says otherwise.** The runbook's variable
  table and the provisioning wizard do not set
  `PDS_ACCEPTING_REPO_IMPORTS` or `PDS_MAX_REPO_IMPORT_SIZE`
  ([runbooks/pds.md](../legacy/runbooks/pds.md)). The production environment
  file is on the host and was not read for this note. A code search of
  `linkjar/infra` on 2026-10-10 found neither name, which does not prove
  they are unset.
- **The cost falls on every account.** The Reference serves all accounts
  from one Node process and one thread; the parity research already
  recorded that the firehose fan-out and the write path share it
  ([2026-10-09-parity-harness.md](2026-10-09-parity-harness.md) §4). A long
  computation in one request delays all others.
- **The effect is on availability.** Nothing in the diff suggests that
  another account's data can be read or changed this way.
- **Not known.** Whether anyone has called `importRepo` on production. The
  edge logs can answer it: `POST /xrpc/com.atproto.repo.importRepo`.

**Answer to the question.** An account holder, and a migrating account, can
reach a code path at 0.5.34 whose work upstream describes as not bounded by
the size of the upload. On LinkJar's deployment the path is open by default
and the cost is shared by all accounts. The size of the effect is not
established.

## 4. #5575, because blobs are in R2

**At the pin every actor store access builds a new S3 client.**
`S3BlobStore.creator()` returns `new S3BlobStore(did, cfg)`, the constructor
builds a client with its own connection pool, and the PDS calls the creator
in `ActorStore.read()` and `transact()`. The pull request reports the
result under sustained `getBlob` traffic: idle connections accumulate until
new requests fail with `EADDRNOTAVAIL`.
Source: [`packages/aws/src/s3.ts`](https://github.com/bluesky-social/atproto/blob/7ca16cc6989f8247637615aca17c5abb911b8fb1/packages/aws/src/s3.ts) lines 82 and 98 to 100;
`packages/pds/src/context.ts` lines 156 to 162 and
`actor-store/actor-store.ts` line 129 at the pin.

**LinkJar uses this store.** Production blobs are in a private R2 bucket
through `PDS_BLOBSTORE_S3_*` ([runbooks/pds.md](../legacy/runbooks/pds.md)).
`getBlob` needs no authentication for an active account. The harness runs
the disk store (`PDS_BLOBSTORE_DISK_LOCATION` in `parity/src/stack/env.ts`),
so the baselines in
[`parity/results`](../../parity/results/perf-reference.md) do not show it.

Upstream treats this as a reliability fix. It is a second decision for the
owner, separate from §5. Evidence to decide it: the count of open
connections from the PDS to R2 on staging under repeated `getBlob`.

## 5. Recommendation

**Keep the pin at 0.5.34 and carry #5584 as a ninth patch.** Until that
image is deployed, set `PDS_ACCEPTING_REPO_IMPORTS=false` in production,
unless move-in is already offered to people. With imports off, the one
handler that takes a tree from a client answers "Service is not accepting
repo imports" before it reads the body.

Reasons:

1. The fix stands alone. Measured: the source part of `a6561d5` (six files,
   all in `packages/repo/src` plus `importRepo.ts`) passes
   `git apply --check` at the pin, and so do its three test files. None of
   the six is among the 97 files the eight patches touch. It was not built
   or run.
2. A pin move brings a product feature under the name of a security fix.
   Email two-factor sign-in is the largest change to the PDS and the OAuth
   provider between the two commits, and 22 of its files are files LinkJar
   patches.
3. The freeze exists so that unit 6 has a fixed target. One patch in the
   repository engine does not move that target; eight rebased patches do.

## 6. What the Rust repository crate must do

These hold for unit 2 whatever the pin decision is.

1. **A tree that reaches one node by more than one path is invalid.**
   `pds-repo` MUST reject it in every operation that reads a tree it did
   not build in the same call: CAR import, diff verification, export, and
   `verify` (SPEC §18.2).
2. **Mark nodes, not record values.** Two records with the same content
   share a value CID and are valid. The rule applies to node CIDs only.
3. **Bound the work by the input.** A traversal of an imported tree MUST
   stop with an error when it has entered more nodes than the CAR has
   blocks. This second guard holds even when a new traversal forgets
   rule 1. Upstream's guard has to be called by each traversal, and its
   contributor documents now say so
   ([`packages/repo/AGENTS.md`](https://github.com/bluesky-social/atproto/blob/a7c8604d876a200a1e4fa4aec83d4189ac4f1c12/packages/repo/AGENTS.md)).
4. **Check order and layer across the whole tree.** SPEC §6.1 already
   bounds entries and depth. Key order across node boundaries and the layer
   of each key are checked for the whole tree and not per node. These
   checks do not replace rule 1.
5. **`importRepo` answers 400 `InvalidRequest`** for such a CAR and writes
   nothing.
6. **The write path never produces one.** A property test over random
   write sequences asserts that no node CID appears twice in the result.
7. **`verify` names it.** A data directory carried over at cutover can hold
   such a repository if the pin accepted one. `verify` MUST report it as
   its own finding, and the cutover runbook needs a rule for that account.
8. **D2 gains a criterion.** `rsky-repo` and the in-house candidate are
   each tested with shared-node trees on import, diff and export. The
   shapes in upstream's
   [`mst-dag.test.ts`](https://github.com/bluesky-social/atproto/blob/a7c8604d876a200a1e4fa4aec83d4189ac4f1c12/packages/repo/tests/mst-dag.test.ts)
   are the vectors, since the interop suite has none. A fuzz target for CAR
   import asserts rule 3.

**Is it a new deliberate difference in SPEC §2.3?**

- **Pin kept, no patch:** yes. It would be DD-6: `importRepo` with a CAR
  whose MST references a node more than once; Candidate 400
  `InvalidRequest`. The Reference column needs a scenario, because what the
  pin answers was not observed. It is a hardening of the kind D16
  describes, so it needs the owner's decision like DD-5.
- **Pin kept, fix carried (the recommendation):** the production Reference
  and the Candidate agree. The Stock Reference still differs, because
  `PATCH_PROFILE=none` applies no patch. §2.3 says a difference holds "in
  every profile" and that the comparison fails when one is missing, so
  DD-6 has to say which target shows it, or the security patch has to
  apply to the stock build as well. Keeping the stock build equal to
  upstream and scoping DD-6 to the stock comparison is the smaller change.
- **Pin moved to 0.5.37:** no. The Candidate matches the Reference.

## 7. Found in passing

- **SPEC §6.5 says the import verifies the commit signature against the
  account's key. The Reference does not.** The handler passes `undefined`
  for the DID and the key (§3). Under §2.3 the Candidate's check is then an
  unlisted difference. It needs a scenario and a decision: list it, or
  follow the pin.
- **#5563 is a D15 case the pin still has.** `createAccount` with the
  handle or email of a deactivated or taken-down account answers 500 at the
  pin and 400 from 0.5.36. It is a candidate for the DD list beside DD-1 to
  DD-4.
- **Two input bounds for `pds-types`.** SPEC §6.1 limits a binary CID to
  100 bytes. Upstream now also refuses a CID string over 128 characters and
  a base58btc key over 128 characters before decoding (#5582, #5583).
- **The weekly check needs a way to be seen.** It fails at the last step,
  after it has computed the bump. A job summary or an issue would have
  shown the three releases without the permission the organization
  withholds.
