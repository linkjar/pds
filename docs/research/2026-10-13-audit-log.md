# Unit 7: the audit log

Date: 2026-10-13 · [Plan](../plan.md) · [SPEC §20](../SPEC.md#20-audit-log)

The Reference keeps no record of who changed an account. This unit gives
the Candidate one that an operator cannot rewrite without it showing.

## 1. Result

| Part | State |
|---|---|
| Entries with a hash chain | Built, in `audit.sqlite`, which takes inserts only. |
| What is recorded | Every `com.atproto.admin` method, the account, credential, identity and invite methods, `importRepo`, and sign-ups and sign-in method changes on the pages. |
| Checkpoints | Built: an RFC 6962 Merkle root signed with Ed25519, every five minutes and at shutdown. |
| Publication | Built: a record of `io.linkjar.pds.audit.checkpoint` in the operator's repository. |
| `audit export`, `audit verify`, `pds-audit-verify` | Built. |
| `audit seal` | Built: the one entry for the history before the log. |

## 2. How it is built

- **`pds-audit`** has the entry format, the Merkle tree, the checkpoint
  and its signer, and the verifier. It reads and writes no file.
- **`pds-storage`** has `AuditDb`. It stores bytes and knows nothing of
  what they say. A trigger on each table refuses every update and every
  delete, so no statement of the server rewrites the log. An append reads
  the last entry and inserts the next in one immediate transaction.
- **`pds-xrpc`** has `AuditLog`. The entry point of the server records a
  method of the audited set after it answered: the caller, the kind of
  credential, the OAuth client, the subject and the outcome. A handler
  names the subject when it is not the caller.
- **The verifier** shares the entry format with the writer and nothing
  else. It builds the tree with a stack where the writer recurses, and it
  writes the bytes that a signature covers by hand where the writer uses
  the DAG-CBOR encoder. A test holds the two trees to the same roots for
  0 to 36 leaves.

## 3. How it is checked

- `pds-audit`: the roots of RFC 6962's test vectors; an export of each
  tree size verifies; each kind of tampering is found (an entry rewritten
  or removed, a checkpoint changed, removed or signed by another key, a
  key under the id of another, a proof for another entry, a wrong anchor).
- `pds-storage`: an update or a delete of an entry, a checkpoint or a key
  is refused by the database.
- `pds-xrpc`: a log is recorded, checkpointed, exported and verified,
  whole and in part; a new key is logged before it signs.
- `linkjar-pds/tests/accounts.rs`: over HTTP, a creation, a refused
  creation and a takedown are in the log, a repository write is not, and
  the export verifies. A checkpoint is published as a record with the
  root of the checkpoint before it.
- `linkjar-pds/tests/cli.rs`: `audit seal`, `audit export` and
  `audit verify` from the command line; a changed bundle exits 1.

## 4. Decisions in this unit

- **The entry is an array.** SPEC §20.2 asks for a fixed field order.
  DAG-CBOR sorts the keys of a map, so the fields are the items of an
  array.
- **The signature covers the hash of the last entry** as well as the
  root, so a checkpoint also pins the chain.
- **The key is a seed in a variable.** D11 leaves the custody of the key
  open between a KMS, an HSM and a file. The seed in
  `PDS_AUDIT_KEY_ED25519_PRIVATE_KEY_HEX` is the file form.
- **An entry is written after the action.** A log that cannot be written
  is an error in the server's log, and the action stands.

## 5. What is not built

1. Entries of the ops console and of the MCP bridge, with the sidecar
   field. They come with units 9 and 10.
2. The reason of an operator action and the request id. The fields are in
   the entry and stay `null`.
3. A checkpoint key in a KMS or an HSM.
4. The metric of the age of the last checkpoint (SPEC §14).
5. A witness that compares checkpoints over time. The records are on the
   firehose for one.
6. An entry whose write fails does not stop the action it records.

## 6. Dependencies

None is new. `pds-audit` uses `ring` for Ed25519 and `sha2`, which the
workspace had.
