# Unit 5, ninth part: OAuth and read-after-write

Date: 2026-10-13 · [Plan](../plan.md) · [SPEC §11](../SPEC.md#11-oauth-authorization-server) · [SPEC §4.5](../SPEC.md#45-read-after-write)

Until this part the Candidate refused every OAuth access token and had no
authorization server. It now authorizes clients, serves their sessions on
the XRPC routes, and adds an account's own writes to six reads of the
AppView.

## 1. Result

| Part | State |

| `POST /oauth/par` | Built. A request object (`request`) is refused. |

| `POST /oauth/token` | Built: `authorization_code` and `refresh_token`. |

`default/20-oauth-flow`, `21-oauth-negative` and `22-oauth-clients` pass
against the Candidate. They drive the official client at the pin and
Chromium through the pages.

## 2. How it is held to the Reference

- **Rows.** The server writes `authorization_request`, `device`,
  `account_device`, `authorized_client`, `token` and `used_refresh_token`
  with the Reference's columns and values: ISO 8601 times, JSON
  `parameters` and `clientAuth`, and identifiers with the Reference's
  prefixes and lengths (`req-`, `cod-`, `tok-`, `ref-`, `dev-`, `ses-`).
  A session that the Reference opened refreshes on the Candidate.
- **Access tokens.** HS256 under `PDS_JWT_SECRET` with `typ: at+jwt` and the
  claims `jti`, `sub`, `iat`, `exp`, `aud` (the service DID), `iss`,
  `client_id` and `cnf.jkt`. The token carries no scope: the scope is in
  the token's row, which the server reads on every request, as the
  Reference does in its stateful mode. Revocation therefore ends an access
  token at once.
- **Lifetimes.** Those of `oauth-constants.ts` at the pin: 60 minutes for
  an access token, 5 minutes for a pushed request and 5 more after each
  step, 2 weeks for a session and a refresh token of a public client, 2
  years and 3 months for a confidential or trusted client, 7 days for a
  sign-in on a device.
- **Client metadata.** `validateClientMetadata` of `client-manager.ts`, rule
  by rule, with its messages. A loopback client gets the metadata that the
  Reference writes for it.
- **Flows.** `RequestManager.validate`, `get` and `setAuthorized`,
  `authorizationCodeGrant`, `refreshTokenGrant`, `compareClientAuth` and
  `revoke` of the Reference, step by step. A code that comes twice and a
  refresh token that comes twice end the session.
- **Scopes.** `transition:generic`, `transition:email` and
  `transition:chat.bsky` grant what `ScopePermissionsTransition` grants.
  The permission scopes `repo:`, `rpc:`, `blob:`, `account:` and
  `identity:` are parsed and checked.
- **Read-after-write.** `read-after-write/` and the six handlers of the
  Reference: the same query for the records after a revision, the same
  check that the store has a record at or before it, the same rules for
  each method, and `Atproto-Upstream-Lag` in place of `Atproto-Repo-Rev`.

Tests: `crates/pds-oauth` (client metadata, DPoP against the RFC 9449
example, PKCE against the RFC 7636 example, scopes, tokens, pages),
`crates/linkjar-pds/tests/oauth.rs` (one flow over HTTP with its refusals)
and `tests/proxy.rs` (an overlaid feed and a feed that passes).

## 3. How the Candidate differs by design

- **Pages.** The Reference ships a browser application that calls a JSON
  API. The Candidate renders each page on the server and takes plain
  forms, as SPEC §11.4 asks. A form carries a token that the server
  computes from the device cookie and the request, and the server checks
  `Origin` and `Sec-Fetch-Site`. The pages keep the contract of
  `parity/README.md`. Since 2026-10-15 a page also loads only by
  navigation, with the Reference's checks of `Sec-Fetch-Site`,
  `Sec-Fetch-Mode`, `Sec-Fetch-Dest` and `Origin`; before, the Candidate
  served a page to a script that the Reference refused.
- **A sign-in that the device does not remember.** The Reference gives the
  browser application a short token. The Candidate puts a signed proof in
  the consent form. The proof names the account, the device and the
  request, and ends after 15 minutes.
- **Scope in handlers.** A method that an OAuth token may call is on an
  allow list. A method with a handler that is not on the list refuses
  every OAuth token with 403, as the Reference's account management does.

## 4. What is not built

Each line is a difference from the Reference or from SPEC §11.

1. The settings of the Reference's account page: the email address, the
   password and the handle. `/account` lists and ends sessions and
   devices only.
2. Request objects (JAR). The metadata says so with
   `request_parameter_supported: false`.
3. Permission sets. An `include:` scope is accepted and grants nothing,
   and the consent page shows a permission scope by its text.
4. Signing algorithms. The Candidate verifies `ES256` and `ES256K` for
   DPoP proofs and client assertions and lists those two. The Reference
   lists ten. SPEC §11.1 names `ES256` only.
5. Introspection. The Reference at the pin publishes no introspection
   endpoint, and the Candidate has none.
6. The reactivation step for a deactivated account. The Candidate returns
   `access_denied` to the client.
7. hCaptcha on the sign-up page, and the password reset from the sign-in
   page.
8. Safe fetch pins no address: the server checks the addresses of a
   client's host and then lets the HTTP client resolve the name again.
9. A sign-up through the pages calls `createAccount` inside the server,
   which also stores a legacy refresh token that nobody holds.
10. The periodic re-fetch of a confidential client's keys. A removed key
    is seen when the cache lets the document go, after 10 minutes or a
    restart.
11. A quoted record in a post that read-after-write adds is asked from the
    AppView, as at the pin. A quoted record of a kind other than a post, a
    feed generator or a list is shown as not found.

## 5. Dependencies

None is new. `pds-xrpc` now depends on `pds-oauth` and on `url`, which the
workspace already had.
