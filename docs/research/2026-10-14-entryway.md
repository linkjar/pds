# Unit 12: a member host and an entryway

Date: 2026-10-14 · [Plan](../plan.md) · [SPEC §21.3](../SPEC.md#213-entryway-and-member-hosts)

A server can now be one of two halves: an entryway that keeps accounts
and sessions, or a member host that keeps repositories. This unit builds
both halves for one member host. It does not build everything §21.3
asks for.

## 1. Result

| Part | State |
|---|---|
| Member host: tokens of the entryway | Built: ES256K, for its DID or for the DID of the entryway. |
| Member host: methods passed on | Built: 19 methods with the credential of the client, 3 admin methods with the admin credential of the entryway. |
| Member host: account creation | Built: a DID and a PLC operation that the entryway signed. |
| Entryway: tokens, sign-up, methods passed to the member host | Built, for one member host. |
| Adoption of a single node | Built: the procedure, and sessions from before go on. |
| OAuth through an entryway | Built: the entryway signs, the member host checks without a session row. |
| More than one member host | Not built. |
| An operation log that resumes after a crash | Not built. |
| The Harness with a member host behind an entryway | Not done. |

The gate of the unit has two parts. "A member host behind the entryway
passes the Harness" is not met: the stack of the Harness has no such
topology. "Adoption changes no DID document" holds by construction: the
old server keeps its address and becomes the member host.

## 2. How it is built

- **One binary, three roles.** A server without the variables of either
  role is the single node. `PDS_ENTRYWAY_*` makes a member host;
  `PDS_MEMBER_*` makes an entryway. A server with both is refused.
- **The member host follows the Reference.** The variables, the checks of
  `createAccount` and their messages, the audience rule for a token and
  the 404 on `/.well-known/atproto-did` are those of the Reference at the
  pin. The Reference has no entryway to read: it is not published.
- **Where this differs from the Reference.** The Reference signs a
  service token with the key of the account for some methods it passes
  on. This server passes on the credential of the client for all of
  them, because the entryway issued that credential and can check it.
- **One audience.** The entryway signs every token for its own DID. A
  member host takes that audience, as the Reference does, so a token
  needs no map from account to host.
- **The entryway is a whole server.** It runs every handler it had. Its
  repositories are empty: a sign-up creates the repository on the member
  host, and a method that is not about accounts goes there.
- **OAuth.** A single node keeps the scope of a session in its row and
  reads the row on every request. A member host has no row, so the
  entryway signs the access token with its key and puts the scope in it,
  as the Reference does behind an entryway.
- **Sessions from before.** A member host answers `ExpiredToken` to an
  access token that its own secret signed. The client then refreshes; the
  member host passes the request on; the entryway takes the old refresh
  token, which the old secret signed for the old server, and answers
  with its own tokens.

## 3. How it is checked

- `crates/linkjar-pds/tests/accounts.rs`, a member host with a test in
  the place of the entryway: the creation of an account and each
  refusal, a write with a token of the entryway, a forged token, the
  methods passed on with their credentials, and the well-known routes.
  This test found that the admin credential of the host went to the
  entryway; it does not go now.
- The same file, an entryway and a member host together: a sign-up, a
  write at each, a sign-in and a refresh through the member host, a
  handle change with its PLC operation, a session from before, and a
  deletion on both.
- `crates/linkjar-pds/tests/oauth.rs`: a client is authorized at the
  entryway and writes at the member host with a proof for the member
  host; a changed token and a proof of another key are refused.
- `crates/pds-xrpc`: the token rules. `crates/pds-identity`: the
  signature and the DID of a PLC operation.

## 4. What is not built

1. **OAuth sessions from before an adoption.** They do not go on: a
   client is authorized again at the entryway. A revocation reaches the
   member host when the access token ends, at most 60 minutes later. A
   session method with an OAuth token at a member host is refused,
   because a DPoP proof names one server.
2. **More than one member host.** The entryway has one, and no map from
   account to host.
3. **The operation log.** A sign-up has three steps on two servers. When
   the last one fails, the entryway removes the repository again. A crash
   between the steps leaves a repository without an account.
4. **Account status.** An account is activated and deactivated at the
   member host. The entryway does not learn it, and a takedown at the
   entryway does not reach the member host.
5. **Large requests and the firehose** through the entryway. A request
   or an answer above 1 MiB is refused there. Clients use the member
   host for uploads, exports and the firehose.
6. **Reconciliation.** Nothing compares the accounts of the entryway
   with the repositories of the member host.
7. **The account database of the member host** keeps its rows from
   before the adoption. Nothing reads the credentials in it.

## 5. Dependencies

None is new.
